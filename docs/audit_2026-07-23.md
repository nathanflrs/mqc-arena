## Q1 — Règle exacte de sélection du gagnant

**Fichier :** `src/arena/selector.py`

La sélection se fait en quatre étapes dans `select_best()` :

### Étape 1 — Override absolu DividendArbitrageAgent (lignes 40-43)
```python
for s in signals:
    if s.meta.get("div_arb_priority") and s.action in ("BUY", "SELL"):
        return s
```
Pendant la fenêtre J-7 → J+1 avant l'ex-date, `DividendArbitrageAgent` court-circuite tout le reste. Le premier signal avec `div_arb_priority=True` gagne inconditionnellement.

### Étape 2 — Score brut (lignes 45-53)
```python
def score_signal(sig):
    if sig.action in ("BUY", "SELL"):
        return sig.confidence * max(sig.target_weight, 0.05)
    return 0.0
```
Score = `confidence × max(target_weight, 0.05)`. Un signal HOLD score toujours 0 et ne peut jamais gagner.

### Étape 3 — Bonus agent prioritaire (lignes 50-52)
```python
if priority_agent and s.agent_name == priority_agent and score > 0:
    score += 0.15  # priority_bonus
```
L'agent prioritaire est `alloc_result.best_agent.get(sym) or AGENT_PRIORITY.get(sym)` (runner.py:620). C'est l'agent avec le meilleur Sharpe glissant pour ce symbole selon le DynamicAllocator. Il reçoit +0.15 sur son score brut.

### Étape 4 — Tri et seuil minimum (lignes 55-61)
```python
scored.sort(key=lambda x: (x[0], x[1].action == "BUY"), reverse=True)
best_score, best_sig = scored[0]
if best_score <= 0.0 or best_score < 0.02:
    return None
```
En cas d'égalité de score, BUY l'emporte sur non-BUY. Le seuil minimum de 0.02 filtre les signaux trop faibles.

### Exemple critique du 23/07 — MSFT
- `MeanReversionAgent` est agent prioritaire (meilleur Sharpe) → aurait dû avoir +0.15
- `EarningsSentimentAgent` émet BUY conf=0.68, target_weight=0.10 → score = 0.68 × 0.10 = **0.068**
- `MeanReversionAgent` émet HOLD → score = **0.0**
- Résultat : EarningsSentimentAgent gagne avec 0.068 sans même avoir besoin de battre le bonus priority (qui s'annule car HOLD score 0 de toute façon)

**Le problème structurel :** le bonus +0.15 ne sert à rien si l'agent prioritaire émet HOLD. Dans ce cas, n'importe quel signal BUY/SELL gagne par défaut.

## Q3 — Chaîne signal → poids cible

### Pipeline complet (runner.py:622-668)

```
AgentSignal.target_weight (config agent)
    ↓ override DynamicAllocator si agent ∈ {Buffett, Citadel, MeanRev, Trend} ET symbole dans cache
    ↓ Kelly blending si round-trips suffisants (min_trades=5)
    ↓ vol_adjusted_weight(df, weight) — réduit sur haute vol
    ↓ plan_from_signal → target_dollars = netliq × target_weight → target_qty
```

### Explication des quatre cas du 23/07

**MSFT — allocation 21%, plan 0.10**
- Agent gagnant : `EarningsSentimentAgent` (non présent dans les 4 agents backtest-ables du DynamicAllocator)
- `alloc_result.weights.get("EarningsSentimentAgent", {}).get("MSFT")` → `None`
- Pas d'override → garde `target_weight=0.10` de `EarningsSentimentConfig` (earnings_sentiment.py:24)
- La table d'allocation de 21% est celle de `MeanReversionAgent`, qui a perdu l'arène sur ce symbole

**GOOGL — allocation 13%, plan 0.04**
- Agent gagnant : `MeanReversionAgent` (présent dans le DynamicAllocator)
- `alloc_result.weights.get("MeanReversionAgent", {}).get("GOOGL")` → `0.04050`
- Override appliqué → plan 0.04
- Les 13% correspondent à `CitadelAgent/GOOGL` dans l'allocateur, pas au gagnant final

**NVDA — Sharpe 1.50, absent du plan final**
- `BuffettAgent` avait gagné l'arène pour NVDA avec conf=0.90
- Le risk manager a évalué NVDA *après* plusieurs BUY déjà approuvés qui ont consommé le budget net long
- NVDA a été rejeté (rejet binaire, pas de rognage) par le risk manager (Rule 2 — net long cap)

**GS — absent de la table d'allocation, plan 0.10**
- GS est dans WATCHLIST (16 symboles) mais absent du cache du DynamicAllocator (`allocator_cache.json` contient 13 symboles : sans GS, BRK-B, JNJ)
- Cause : lors du run partiel du 23/07 matin (avant le fix download), GS avait échoué → pas entré dans `all_data` → pas inclus dans le calcul DynamicAllocator ce jour-là
- Résultat : `dynamic_weight = None` → fallback vers `target_weight=0.10` de `BuffettAgent` hardcodé

**Diagnostic :** la chaîne n'est pas déterministe d'un seul chemin. Elle bifurque selon (a) si l'agent gagnant est backtest-able, (b) si le symbole est dans le cache allocator. Ces bifurcations sont implicites et non loguées.

## Q4 — Risk Manager : ordre et logique de rejet

**Fichier :** `src/risk/manager.py`

### Ordre d'évaluation
Les plans sont évalués dans l'ordre exact de la liste en entrée, qui correspond à l'ordre de `WATCHLIST` dans le runner (runner.py:613). **Aucun tri par conviction avant évaluation.**

### Règles par ordre d'application (pour chaque plan BUY)
1. Kill switch sell-only → rejet immédiat
2. Rule 1 — Position max (20% NAV) → rejet si `target_dollars > 0.20 × netliq`
3. Rule 2 — Net long max (45% en `bull_volatile`) → rejet si `projected_long > seuil × netliq`
4. Rule 3 — Cash floor (30%) → rejet si `projected_cash < 0.30 × netliq`
5. Rule 4 — Liquidité ADV (1% vol quotidien) → rejet si `est_notional > 0.01 × adv`

**Le rejet est strictement binaire.** Il n'existe aucun chemin de rognage dans le risk manager. Un BUY est approuvé en intégralité ou rejeté en intégralité. Les variables `projected_long_notional` et `projected_cash` sont mises à jour en place au fil de l'évaluation — ce qui crée l'effet sac-à-dos glouton décrit en P3.

### Pourquoi GOOGL passe à 0.04 et NVDA est rejeté

GOOGL n'a pas été rogné par le risk manager — il est entré avec `target_weight=0.04` (venant de l'allocateur, voir Q3). Avec `est_notional ≈ $4,050` sur un netliq de $1M, il passe toutes les règles sans difficulté.

NVDA avait `target_weight=0.12` → `est_notional ≈ $123k`. Au moment où le risk manager l'évalue (après AAPL, SPY, GOOGL déjà approuvés), le budget net long restant est insuffisant → Rule 2 → rejet binaire.

**Le problème :** NVDA (Sharpe 1.50, conviction forte) est éliminé au profit de plans approuvés antérieurement uniquement parce qu'il apparaît plus tard dans WATCHLIST et qu'il est plus gros.

## Q6 — Signaux dégénérés : VolatilityAgent et MacroAgent

### VolatilityAgent (`src/agents/volatility.py`)

L'agent télécharge `^VIX` **une fois par instance** avec un cache en mémoire de 5 minutes (`_VIX_TTL = 300`, ligne 75). La méthode `_analyze_vix()` (ligne 82) retourne un dict `{vix, zscore, mom5, vix_ratio}` partagé entre tous les appels de la même instance.

**Le générateur de signal (lignes 118-200) ne lit aucune variable `data` (OHLCV du symbole).** Le seul paramètre symbole-spécifique est `portfolio.get(state.symbol, 0.0)` pour distinguer une position déjà ouverte. Résultat : tous les symboles non détenus reçoivent un signal identique (HOLD conf=0.30 en régime VIX modéré). Tous les symboles détenus reçoivent un autre signal identique. Ce n'est pas 14 signaux — c'est 1 ou 2 signaux recopié 14 fois.

**Confirmation chiffrée :** sur le run du 23/07, VIX=19.5, zscore=0.42, mom5=16.6% identiques sur les 14 lignes du log.

### MacroAgent (`src/agents/macro.py`)

Chemin FRED (ligne 130) : `score_fred_indicators()` produit `(risk_on, risk_off)` à partir de T10Y2Y, HY OAS, VIX, Fed funds trend — toutes séries macro-globales. Ces scores sont **identiques sur les 14 symboles** d'un même run.

Le seul élément symbole-spécifique : `_ticker_momentum()` (ligne 311) — momentum 63j du ticker individuel. C'est une porte binaire (>+2% → BUY gate ouverte, <-2% → SELL gate ouverte). En bull market, tous les titres passent la porte BUY simultanément.

Résultat net : `Macro MIXED: risk_on=3 risk_off=0` identique sur 13 des 14 symboles du 23/07. L'agent n'est symbole-spécifique qu'à la marge.

### Conclusion Q6

**VolatilityAgent :** signal 100% global, 0% symbole-spécifique.  
**MacroAgent :** signal ~95% global, ~5% symbole-spécifique (gate binaire).  

Ces deux agents ajoutent 28 lignes par run dans `decisions.csv` pour une information qui se résume à 2 états globaux. Ils faussent les statistiques de participation et consomment du temps de traitement sans discriminer les symboles entre eux.
